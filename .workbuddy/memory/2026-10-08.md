## F8 深挖（当时是设计讨论；方案已被采纳并落地，见文末）

**关键发现：谱系不用猜，已躺在 store 里。** `crawl.sources[].url` 记着源目录（`D:\Obsidian Vault`，
`kind: 'local'`），产物目录 = `sourceDirOf(name)` = `~/.nx-kn/sources/<name>`。所以
「`sources\obsidian-vault` 派生自 `D:\Obsidian Vault`」是一条**现成的边**，靠内容哈希去猜是下策。

**零代码 `kb remove` 不持久（重要）**：`crawl/service.js:864` 的自动登记条件是
`produced > 0 && !已存在` → **删掉产物库后，下次 `pipeline` 会把它重新加回来**。
删源库（`D:\Obsidian Vault`）则稳定——自动登记只认产物目录，不会登记源目录。

**建议的分层（按优雅度排序，后一条比前一条更省接口面）**：
- 处置层（解决存量）：`kb.vaults[]` 加 `standby`，`kb/service.js:72 resolveVaults` 默认过滤（index/query/status 共用此函数，一处生效三处）。
- 预防层（不再制造新的）：`crawl/service.js:864` 自动登记前查 `s.url` 是否已是登记库，是则不登记第二个。
- **更优雅的合体（推荐，无需新 action）**：kb.vaults 记录加 `auto: true`（仅由 crawl 自动登记写入）；
  解析时 `auto === true` 且其源库也在列表中 → 默认排除。**用户显式 `kb add <产物路径>` 即清掉 auto → 参与检索**，
  等于用已有命令表达"我确认要它"，不必新增 `kb standby`。存量数据无此字段时，用谱系推导
  （`path === sourceDirOf(s.name) && s.url 也是登记库`）兜底判为 auto。
  配套：`kb status`/`pipeline` 要把"因重叠而未参与"明说出来，避免变成静默不索引。
- 提示层：`kb list`/`status` 用上面的谱系边报「这两个库内容重叠」。
- 判据冲突点：**预防层默认"不脏"（宁可少），standby 默认"不漏"（宁可重复）**。个人知识库宜偏"不漏"，
  故推荐「预防层不制造新重复 + 同判据兜存量」，而不是把默认改成排除一切自动登记库。

**当时的待拍板项**：留原库（时效好）还是留整理产物（结构好但要 crawl run 才更新）——后由用户一句「ok」拍板：
**不二选一，改为机制化**（下方）。

## F8 已落地：抓取产物与源库重叠时，默认只留源库参与检索

**用户拍板的方向**：不做「数据取舍」（删哪个库都是错的，因为两者各有用途），改为**机制**——让「产物默认不参与检索、
需要时一条已有命令即可启用」成为默认行为。落地方案在三层里选的是**预防层 + 解析期过滤 + 复用 `kb add` 作启用口**，
**不新增专门命令**（新增 `kb standby` 反而多一个接口面）。

**判据不是猜的，是 store 里现成的边。** 谱系完全确定：`crawl.sources[].url` 记源目录（本地源 `kind:'local'`），
产物目录 = `sourceDirOf(源名)` = `~/.nx-kn/sources/<源名>`。两条路径都是 nx-kn 自己写下的，不靠内容哈希/相似度
（产物是重排版 + 加 frontmatter，哈希与路径都对不上）。这就是「够优雅」的根：判据确定、可解释。

**三态 `origin`（新增字段，向后兼容）**：`'crawl'`（crawl 自动登记写入）/ `'user'`（显式 `kb add` 写入）/ `null`
（历史记录，字段不存在）。**只有 `origin !== 'user'` 才可能被抑制**——用户明确加过的库永不被自动排除。

**落点（8 处）**：
- `core/store.js`：`normalizeVault` 增 `origin`（非法值一律归 `null`）；新增纯函数
  `crawlProductVaults(store)`（→ `Map<产物路径, 源路径>`）与 `standbyVaults(store)`。
  成边条件三条缺一不可：产物目录已登记 + 源目录 `s.url` 也已登记 + 源 ≠ 产物。web 源不参与（`url` 是网址不是目录），
  源未登记不抑制，源==产物（病态）不算。
- `modules/kb/service.js`：`resolveVaults` 返回从「一个大数组」改成 **`{ vaults, standby, source }`**——
  刻意拆开，防调用方漏看标志位把重复静默算进去。`add` 对新建与已存在记录都写 `origin:'user'`（**已存在的库再
  `kb add` 一次 = 启用**，用已有命令表达「我确认要它」）；`--root` / 环境变量分支是**逃生舱，不参与抑制**。
  `status` 的 `totals.vaults/indexed/stale/notes` **只统计参与检索的库**，另给 `suppressed` 与 `standbyNotes`。
  `query` 的 `skipped[]` 把「被规则排除」与「出错跳过」用不同字段区分（`standby:true` + 专用文案）。
  新增 `standbyNote(v)` 统一说法：`与源库 [X] 内容重叠（抓取产物），默认不参与检索——要用它跑 nx-kn kb add "<path>"`。
- `modules/crawl/service.js`：自动登记处写 `origin:'crawl'`；识别 `s.url` 是否也是登记库 → 记 `overlapsWith`，
  返回 `standby`/`overlapsWith`，`note` 追加重叠说明。**这层是预防层：不再制造新的静默重复。**
- 呈现层：`kb/index.js`（CLI）四处 + `kb/view.jsx`（面板）——库行加 `未参与检索` 标签与 **`启用检索` 按钮**
  （走 `POST /api/kb/add`）；`home/service.js` 的 pipeline 索引步骤区分「没有知识库」与「都判为重复」。

**本机真实数据差异（只读复核，未改磁盘）**：源库 `D:\Obsidian Vault` 可索引 **173** 篇（zg 跳过 1 个克隆仓库
48 篇 + 5 篇空文件），产物 `sources\obsidian-vault` 是 **226** 篇 = 173+48+5（产物把克隆仓库也收了）。
所以「留源库」在真实数据上意味着那 48 篇克隆仓库不再进检索——**与 zg 默认口径一致，但是真实内容增减**，不是纯
「去掉重复」。真实 `kb list` → `共 2 个知识库（其中 1 个默认不参与检索）`；`query "前端流程"` → `检索了 1 个库`
外加一行 `未参与 [obsidian-vault] ...`。**用户本机磁盘零改动**（只读）。

**测试**：新增 `tests/unit/vault-lineage.test.mjs`（11 条，钉住谱系边界：web 源不误判 / 源未登记不抑制 /
源==产物不算 / `origin:'user'` 永不被排除 / `--root` 是逃生舱 / `kb add` 一次即启用）；`kb-store.test.mjs`
断言形状补 `origin: null`；`tests/pipeline.mjs` 新增 **P19** 端到端（kb add 源库 + crawl run → 默认只留源库 →
kb add 产物 + index → 产物真能搜到）。unit 119 → **130**。

**P19 的坑（值得记）**：第一版断言「`kb add` 之后产物参与检索」失败——根因是**被排除的库从不进 `index`**，
所以 `kb add` 之后它仍无索引，`query` 自然搜不到。修复 = `kb add` 后补一步 `index`，并加 `--limit 20` 防多库下被挤掉。
断言也拆成两层：「规则层面」（`list` 里 `standby===false`）与「行为层面」（建索引后真能搜到）。
