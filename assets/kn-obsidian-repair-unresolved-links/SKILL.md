# Obsidian 未解析双链补全

**触发：**

- 用户说 "[[某某]] 没创建" / "修复未解析链接" / "双链不存在"
- 用户说 "obsidian 还有未解析的 link" / "wiki-link 打不开"
- 批量补全 vault 里的 `[[]]` 红链
- 处理问句型双链（读者提问型 `[[xxx]]`）

**核心约束**：所有未解析双链都要创建笔记——问句也是。绝不删除、绝不改成引用块、绝不跳过。

**工具**：本 skill 只有一条依赖——**nx-kn CLI**。扫描、生成 frontmatter、校验、取规范，全部是 nx-kn 的命令；本 skill 不带脚本、不需要 python。

---

## 这个 SOP 怎么用

整条流程是 **9 步**，外加 4 个特殊场景（问句型双链 / 问卷模式 / **项目解读** / 并发）。每一步的**关键上下文**都从 nx-kn CLI 拿——你不需要知道文件在哪，命令会告诉你。

| 步骤                     | 拿上下文的命令                                       | 这一步要干什么                         | 产出                     |
| ------------------------ | ---------------------------------------------------- | -------------------------------------- | ------------------------ |
| **0. 拿规范**      | `nx-kn obsidian spec` → `spec --doc <key>`      | 列出登记的规范，取本次要用的那几份全文 | 规范全文 + vault 根      |
| **1. 查看**        | `nx-kn obsidian scan --json`                       | 扫出全库未解析双链                     | 链接 + 出处（文件:行号） |
| **2. 过滤**        | （scan 已自动排除）                                  | 剔掉附件与模板占位链接                 | 待处理链接               |
| **3. 定位**        | Grep（可选）                                         | 读 source 上下文，理解这条链接指什么   | 上下文摘要               |
| **4. frontmatter** | `nx-kn obsidian frontmatter --source … --link …` | 生成合规 YAML 段                       | `---` 包裹的 YAML      |
| **5. 修文件名**    | 同上（看 `filename` 字段）                         | 人工判断标点要不要改写                 | 最终文件名               |
| **6. 生成内容**    | （按步骤 0 取到的内容规范）                          | 写深入、不重复的正文                   | 正文                     |
| **7. 创建**        | Write                                                | 写到 source 同目录                     | 新笔记文件               |
| **8. 校验**        | `nx-kn obsidian check --snapshot-before …`        | 确认新笔记没引入新红链                 | passed=true/false        |
| **9. 验证**        | `head -3` / 再跑一次 `scan`                      | frontmatter 在位、链接消失             | 收尾                     |

## 步骤 0：拿规范与上下文（先于一切步骤）

**规范不在本 skill 里**——内容模式、问卷模式、frontmatter 细则都由用户维护在 vault 里，**用户随时可以改**。所以动手前先列清单、再按用途取：

### 0.1 列出全部登记的规范

```bash
nx-kn obsidian spec
```

输出形如：

```
vault: D:\code\a_md\obsidian_init
规范文档登记项（3）:
  content          nx-kn/base-content.md  【存在】
  questionnaire    nx-kn/questionnaire.md  【存在】
  frontmatter      nx-kn/frontmatter-spec.md  【存在】
```

**先看这份清单**：哪些规范在（【存在】）、哪些缺（【缺失】）、以及它们的 key 叫什么。
**key 是用户自定义的**——下面的用途↔默认 key 只是常见约定，**以清单里实际有的为准**。

### 0.2 按用途取具体那几份

```bash
nx-kn obsidian spec --doc content          # 内容生成规范（步骤 6 照它写）
nx-kn obsidian spec --doc questionnaire    # 问卷模式规范（问卷模式才需要）
nx-kn obsidian spec --doc frontmatter     # frontmatter 细则（步骤 4 有疑问时）
```

这条命令**直接输出规范全文**——照着写就行，不需要知道它在哪。

> 清单里**没有**对应用途的那一份（比如没有 `questionnaire`），说明用户没登记它：
> **停下来问用户**「要不要补一份？还是直接按步骤 6 的通用要求写？」——不要凭记忆编规范内容。

### 0.3 vault 根（脚本与检索都要绝对路径）

```bash
nx-kn obsidian get --json
```

**vault 在哪，只认这条命令的答案**（`vault` 字段）。它来自用户的配置——web 面板「Obsidian」页
或 `nx-kn obsidian set vault=<路径>`，**设置一次，所有命令都从配置读**。skill 不自己选库。

**未设置时**（返回 `configured:false`）：**停下来问用户**要 vault 路径，让用户在面板里填、
或 `nx-kn obsidian set vault=<路径>` 登记一次。不要沿父目录去猜——猜错库比多问一句贵得多。

## 流程（9 步）

```
1. 查看 → 2. 过滤 → 3. 定位 → 4. 生成 frontmatter（硬性）──┐
                                                          ↓
                                   5. 修文件名（sanitization）──┐
                                                              ↓
                                6. 生成内容（按内容规范）──────┤
                                                              ↓
                            7. 创建到 source 同目录 ────────────┘
                                                              ↓
            8. 双链引用校验（snapshot diff）──┐
                                          ↓
                  9. 验证（head -3 + 再扫一次）─┘
```

### 1. 查看

```bash
nx-kn obsidian scan --json
```

**输出形态**：

```json
{
  "status": "ok",
  "via": "builtin",
  "count": 2,
  "links": [
    { "link": "xxx", "sources": [{ "file": "日常/foo.md", "line": 9 }] }
  ]
}
```

`via` 标明实际来源：`builtin` = 内置解析（默认）；`cli` = 用了 obsidian 命令行（它与 Obsidian 实际解析最接近）。两种都可信，行为差异见下文「来源差异」。

### 2. 过滤

排除：

- **图片 / 附件链接**（`.png` / `.jpg` / `.pdf` / `.zip` 等）——Obsidian 当附件处理（`scan` 已经自动排除）
- **模板文件** `ctl/tmpl_*.md` 中的占位示例链接（`scan` 已经自动排除）

### 3. 定位

`scan` 的输出里已经带 `file` + `line`，不必再 Grep。要上下文就：

```bash
grep -rn "\[\[xxx\]\]" --include="*.md" 日常/  # 排除 ctl/、.claude/、.zvec-grep/
```

记下 `{file}`、`{line}`、前后 3 句上下文（用于步骤 6 理解链接含义）。

### 4. 生成 frontmatter（硬性步骤，不可跳过）

```bash
nx-kn obsidian frontmatter --source 日常/foo.md --link "xxx" --locate
```

命令输出的 YAML 段（`---` 到下一个 `---` 之间）就是新文件的 frontmatter，**直接复制到 Write content 的开头**。

**为什么必须用命令、不能自己手写 frontmatter：**

- 时间戳格式 `creatime: 2026-XX-XX HH:MM:SS` 一致
- `bklink` 自动指向 source 文件（避免反向链接断裂）
- `tags` 默认空数组（否则聚合报错）
- `--locate` 会把**全库引用了这个链接的笔记**都写进 bklink（`--source` 指向的文件不必存在）

命令默认生成三段：`creatime` / `tags` / `bklink`，不依赖 vault 里的任何模板文件——拿过来就跑。
各字段被谁用、bklink 的完整语义、sanitization 细则 → 见步骤 0 取到的 frontmatter 规范。

### 5. 修文件名（sanitization）

命令输出的 `filename` 字段是清洗后的文件名；**主线程同时人工检查 link 内容是否含 `, . ?` 等 Obsidian 不支持的标点**——见下文「标题 sanitization 规则」。

### 6. 生成内容

按步骤 0 取到的**内容规范文档**的规范写。读 `{file}` 上下文后生成**深入、不重复**的笔记。

**主题 → 模式** 的映射（内容规范里也是这么分的）：

| xxx 形态           | 模式                                    |
| ------------------ | --------------------------------------- |
| 名词短语 / 概念    | 模式 A 概念深潜 / 模式 D 概念拓扑       |
| 动词 / 操作        | 模式 B 实践拆解 / 模式 C 还原论拆解     |
| 问句 / 批注 / 反馈 | 模式 B 实践拆解（整篇写一篇针对性回答） |

锚点前置、量级感知、trade-off 讨论——具体定义见内容规范文档。

**生成前先在 vault 内搜相关笔记避免重复**：用 `mcp__zvec_grep__zvec_grep_search`（`query` = `{link}` 字面 + 源上下文一句话摘要，`limit` = 10）；MCP 不可用时回退 Grep，关键词从 `{link}` 字面和源上下文提炼 2-4 个组合 OR 检索。

### 7. 创建文件到 source 同目录

**强制规则**：新笔记必须创建在 source 文件所在目录下，绝不放 vault 根。

```
✅ 日常/如何成为一个动画制作工程师.md  (source)
   → 日常/动画工程师需要养成哪些直觉.md  (新文件)

❌ 根目录/动画工程师需要养成哪些直觉.md  (丢到根目录 = vault 混乱)
```

根目录只放 `base-root.md` 这类 vault 入口；具体笔记按 source 目录归属。

### 8. 双链引用校验

**不能只看 source 那边的链接是否消失**——新文件**内部**的双链也要逐个能解析。做 snapshot diff：

```bash
# 写笔记前：snapshot 当前 vault 的 unresolved 状态
nx-kn obsidian check --snapshot snapshot.json
# ... 写新笔记（步骤 6+7） ...
# 写完后：diff snapshot，识别新文件引入的失败双链
nx-kn obsidian check --snapshot-before snapshot.json --new-file "日常/动画工程师需要养成哪些直觉.md"
```

输出 `[OK] 新文件 … 未引入新的未解析双链` 或 `[FAIL] … 引入了 N 个未解析双链` + 常见根因诊断。
**判断依据是 JSON 里的 `passed` 字段**（`true` = 通过），不要靠退出码。

### 9. 验证

- `head -3 <新文件>` 第一行必须是 `---`（YAML 起始）
- `head -10 <新文件>` 必须能见到 `creatime:` / `tags:` / `bklink:` 三段
- 再跑一次 `nx-kn obsidian scan --json`，确认刚才那个链接不见了

## ⚠️ frontmatter 强制约束（必读）

**这是本 skill 最重要的一条规则，违反会导致 vault 一致性破坏：**

> **Write 调用的 content 字符串的第一个字符必须是 `---`（YAML 起始），文件最开头 3 行必须是有效的 YAML frontmatter。**

### 漏 frontmatter 的实际危害

- Obsidian **双链反向链接**失效（`bklink` 缺失）
- **Dataview 查询**查不到（`creatime` / `tags` 缺失）
- **Tags 聚合**失败（`tags: []` 缺失）
- **Templater / QuickAdd** 等插件的"按 frontmatter 处理"功能全部失效

### 反例：错误的 Write 调用

```text
# ❌ 错误（bad_eg 1）：content 第一个字符是 '#'
---
# 高级语言抽象层次与性能损失
> 关联笔记：...
---

# ❌ 错误（bad_eg 2）：用 === 代替 --- 包裹 frontmatter
# nx-kn obsidian frontmatter 输出的是标准 YAML（--- 包裹），
# 但 AI 有时误把 prompt 模板中的 === 节分隔符当成 YAML 语法
---
===
creatime: 2026-06-21 14:00:00
tags: []
bklink: []
===
# 标题
正文...
---
```

> ⚠️ **`===` 的角色：** prompt 模板中的 `=== FRONTMATTER ===` / `=== 任务 ===` 是**模板节分隔符**，告诉 subagent 每段从哪里开始。里面的 YAML 内容（即 `{frontmatter_yaml}`）始终是 `---` 包裹的标准 YAML。subagent 写文件时**必须用 `---` 包裹 frontmatter**，不要照抄 `===`。

### 正例：正确的 Write 调用

```text
# ✅ 正确：先跑 nx-kn obsidian frontmatter，把输出放在 content 开头
---
creatime: 2026-06-16 14:59:59
tags: []
bklink:
  - "[[base_日常]]"
---
# 高级语言抽象层次与性能损失
> 关联笔记：...
```

（然后 Write 这个路径，内容就是上面那一整段。）

## 相关性搜索（避免重复）

**触发：** 步骤 6、subagent prompt 步骤 3 的"链接 vault 内已有相关笔记，避免重复"——写新笔记前先确认主题在 vault 里没撞车。

### 工具路由（按此顺序选）

| 顺序 | 工具                                                   | 何时用                                                        |
| ---- | ------------------------------------------------------ | ------------------------------------------------------------- |
| 1    | `mcp__zvec_grep__zvec_grep_search`（**首选**） | MCP 工具列表中存在该工具时一律先用这个                        |
| 2    | **`Grep`**（**仅回退**）                 | `mcp__zvec_grep__zvec_grep_search` 在当前 host 不可用时回退 |

**1 用 zvec_grep_search 的原因**：

- vault 笔记主题分散、措辞漂移（"游标跨页方案" vs "keyset pagination"、"双链修复" vs "broken wiki-links"）——词法 grep 关键词随新笔记累积失效
- 语义检索按概念召回，不被关键词绑定；MCP 后台增量刷新索引，无需手动维护
- 不需要为每个新链接挑选关键词；query 直接用 `{link}` 字面 + 源上下文一句话摘要

**调用参数**：

- `root` = `{vault_root}`（步骤 0.3 从 `nx-kn obsidian get` 读到的 `vault` 字段）
- `query` = `{link}` 字面 + 源文件 {line} 行前后 1-3 句的一句话摘要
- `limit` = 10（够用即止，避免噪音）
- 不需要 `fuse` / 不需要 `queries` / 不需要 `vector`：单组语义检索足够

**2 Grep 回退**：

- 关键词：从 `{link}` 字面 + 源上下文提炼 2-4 个中英文关键词，OR 组合；目录限定为 vault 根（不要搜 `ctl/`、`__pycache__`、`.zvec-grep/`、`.claude/`）
- grep 命中后必须再过一遍语义判断——字面命中不代表主题真的相关

### 反模式

- ❌ 先 grep 几轮没结果就放弃，跳过"避免重复"直接写笔记——主题撞车比耗时更糟
- ❌ 用 zvec_grep 一搜 0 结果就断定"vault 没相关笔记"——可能是 query 太宽或太窄，重写 query 再搜一次
- ❌ 用 grep 时跨目录搜到 `ctl/`（模板占位链接）、`.zvec-grep/`（索引）、`.claude/`（skill 代码）——这些目录里的"命中"全是噪音

## 并发模式

当存在 **多个未解析链接** 时：

```
发现 → 定位 → 元数据（主线程跑 frontmatter）  ← 步骤 4 硬性
              │
              ▼  把命令输出（YAML 段）注入下面 prompt 的 {frontmatter_yaml} 占位符
              ├── subagent 1: 读上下文 → 生成内容（步骤 6） → 创建文件（步骤 7）
              ├── subagent 2: 读上下文 → 生成内容（步骤 6） → 创建文件（步骤 7）
              └── subagent 3: 读上下文 → 生成内容（步骤 6） → 创建文件（步骤 7）
              │
              ▼  所有 subagent 完成后，主线程跑一次 check（步骤 8）
```

**关键约束：**

- 主线程必须在派发 subagent **之前** 跑完 `nx-kn obsidian frontmatter`，把命令输出的 YAML 段（即 `---` 到下一个 `---` 之间的内容）复制到 subagent prompt 的 `{frontmatter_yaml}` 占位符位置。subagent **不要自己写** frontmatter——直接用主线程注入的 YAML。
- 主线程还要先跑 `nx-kn obsidian spec` 拿清单、按用途取正文，并把**内容规范文档的路径**注入到 `{content_spec}` 占位符（subagent 自己 Read 那一份——规范可能很长，复制进每个 prompt 是浪费）。
- 所有 subagent 完成后，主线程**统一跑一次** `nx-kn obsidian check`（步骤 8），校验所有新文件内部的双链
- 每个 subagent 单独跑 prompt 内的 `head -3` 自检 frontmatter（步骤 9 子步骤）

### Prompt 模板（所有 `{xxx}` 都是占位符，必须由主线程替换）

派发前，主线程执行：

```bash
# 0. 拿规范清单与要用的那几份
nx-kn obsidian spec
nx-kn obsidian spec --doc content
nx-kn obsidian get --json

# 1. 拿 frontmatter YAML（{frontmatter_yaml}）
nx-kn obsidian frontmatter --source {file} --link "{link}" --locate
# 把输出里 --- 到 --- 之间的内容抓出来，替换 {frontmatter_yaml}
```

然后把替换后的整个 prompt 喂给 subagent：

```
=== 下方 YAML 是主线程已生成的 frontmatter，subagent 必须原样作为 Write content 开头（注意：用 --- 包裹，不是 ===）===
{frontmatter_yaml}
===

=== 任务（占位符在派发前已替换为具体值）===

1. 源文件 {file} 第 {line} 行引用了 [[{link}]]
2. 读源文件上下文，理解链接含义
3. 先读 {content_spec}（内容规范文档的绝对路径，主线程已解析），生成内容以它为准
   - 若 {content_spec} 仍是占位符：先跑 `nx-kn obsidian spec` 拿清单、再跑 `nx-kn obsidian spec --doc <key>` 取全文；再失败则从 {file} 沿父目录找 `.obsidian`，默认取 `<vault>/nx-kn/base-content.md`
   - 根据主题选择对应模式：概念深潜 / 实践拆解 / 还原论拆解 / 概念拓扑
   - 锚点前置：第一段先给具体问题或反直觉现象
   - 量级感知：用具体数字，不用"快"、"慢"、"大量"
   - trade-off 讨论：展示工程妥协而非列出"优点"
   - **找 vault 内相关笔记避免重复**：见上文「相关性搜索」——首选 `mcp__zvec_grep__zvec_grep_search`（`root` = `{vault_root}`，`query` = `{link}` 字面 + 源上下文一句话摘要，`limit` = 10）；MCP 不可用时回退 Grep，关键词从 `{link}` 字面和源上下文提炼 2-4 个组合 OR 检索

=== 输出要求 ===

- Write 的 content 字符串必须以 === 下方 YAML 块的内容开头（该内容是 --- 包裹的标准 YAML，subagent 直接复制）
- 注意：YAML 块用 `---` 包裹，不要因为看到 === 就照抄 ===
- 然后接 # 标题 和正文
- 文件名 {safe}.md，写入 source 文件同目录（如 source 在 `日常/` 下，则写 `日常/{safe}.md`）
- 写完后用 Read 工具读回前 3 行验证 frontmatter 存在
```

## 问卷模式（特殊需求时）

**触发条件：** 源文件是问卷模板（含问题 + 用户填写内容），且用户要求生成定制化响应。

**判断特征：**

- 源文件包含问题列表（段落 / 表格）和用户填写内容
- 末尾有触发双链，如 `[[我已经完成了问卷 帮我规划吧]]`

**处理方式：**

1. 读取源文件，解析用户的所有问卷回答
2. 分析关键数据：约束条件、偏好 / 厌恶、限制因素、基线能力
3. 读取问卷规范（步骤 0.2 取到的 `questionnaire` 那一份）获取问卷模式的写作规范
4. 生成与用户情况匹配的针对性响应
5. 写入位置：
   - 如果触发双链是"响应锚点"（如 `[[xxx规划]]`）→ 直接写入该文件（文件在 source 同目录）
   - 如果触发双链是"新建笔记名"（如 `[[张三的4周计划]]`）→ 在 source 同目录创建独立文件

> ⚠️ 无论是哪种情况，**文件必须放在 source 同目录**，不要丢到 vault 根目录。

## 项目解读场景（读大项目 → 生成文档 → 双链拷问）

**触发：** 在代码项目里被要求「读这个项目 / 给它写文档」，或用户对项目文档写了 `[[问题]]`。

这个场景的 SOP 与主流程**只差两处**：入口多一条脚本；答案是**带着项目源码**写的，不是凭文档复述。

| 环节       | 怎么走                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------- |
| **两个根** | 项目根 = 代码仓库根（`git rev-parse --show-toplevel`）；vault 根 = `nx-kn obsidian get --json` 的已配置 `vault`（`source=cwd` 是猜测值，先确认再用） |
| **初始化** | 首次解读先跑 `nx-kn obsidian ask --project <项目根>`（不带提问）：脚本建 `<vault>/projects/<项目名>/Base-<项目名>.md`（frontmatter 带 project 绑定）；**每篇文档只讲一个单项**，层级关系由双链建立（bklink 指父节点），根文档不维护清单 |
| **提问**   | 项目域提问**一律先跑脚本** `nx-kn obsidian ask --question "<原始提问>" --project <项目根>`：脚本把提问清洗成合法文件名、以 `[[…]]` 追加到根文档**末尾**（重复提问不重复追加），并返回答案笔记位置 `note.path` → 然后走标准 9 步；步骤 6 读到 source 的 `project` 字段 → **必须读源码**作答，引用 `文件:行号` |

**位置只由 `ask` 脚本决定，agent 不自行创建位置（硬性）：** 答案笔记写到它返回的 `note.path`；
步骤 3 的出处用脚本返回的 `base.rel` + `line`，不用再 Grep；除 `Base-<项目名>.md` 外
**禁止创建任何文档树 / 索引 / MOC / 清单文件**——树只靠 bklink 长出来
（历史教训：agent 反复冗余地建树建索引，这不是期望行为）。
细节见 `references/10-project-mode.md`。

## 问句 / 批注 / 反馈型双链处理（特殊场景）

**核心原则：所有未解析双链都要创建笔记。** 哪怕 `[[xxx]]` 看起来是问句 / 批注 / 反馈 / 吐槽，**也创建笔记**——AI 把 xxx 当作读者提问，写一篇针对性回答。

### 三种情况，统一动作 = 创建笔记

| # | `[[xxx]]` 形态                             | 处置                                                       |
| - | -------------------------------------------- | ---------------------------------------------------------- |
| 1 | xxx 像文件名 / 概念短语                      | 创建笔记（标准流程）                                       |
| 2 | **xxx 像问句 / 批注 / 反馈 / 吐槽**    | **也创建笔记**——AI 把 xxx 当提问，写一篇针对性回答 |
| 3 | xxx 内部有格式问题（空格 / 标点 / 全角括号） | 重写 `[[xxx]]` 为合法双链（修正格式）→ 创建笔记         |

**唯一被允许的"重写格式"** = case 3 修正 `[[]]` 内部的格式问题，**重写完还是创建笔记**。

**绝对禁止：**

- ❌ 删除 `[[xxx]]`（丢弃读者意图）
- ❌ 改成 `> 读者提问：xxx`（这是丢弃，不是补全）
- ❌ 把问句理解成"伪双链"而跳过创建

### 案例 2 的执行 SOP（`xxx` 是问句 / 批注 / 反馈时）

1. `[[xxx]]` 是问句（如 `[[你这个文档在解释什么东西]]`）
2. **照样创建新文件**，文件名 = sanitized 后的 xxx
3. 文件首段以 `> 关联上下文：[源文件链接]` 开头，点明来源
4. **整篇笔记围绕 xxx 写一篇针对性回答**：
   - 模式 A 概念深潜：先答"是什么" + "为什么" + 边界
   - 模式 B 实践拆解：举具体场景 / 参数 / 翻车案例
   - 不要写"xxx 是什么的定义"——直接进入正文
5. frontmatter `bklink` 加 `[[源文件]]`
6. 跑步骤 8 `nx-kn obsidian check` 校验

### 案例 3 的格式修正 SOP（`[[xxx]]` 内部格式有问题时）

| 错误格式                       | 修正后                              | 备注                         |
| ------------------------------ | ----------------------------------- | ---------------------------- |
| `[[xxx　yyy]]`（全角空格）   | `[[xxx yyy]]` 或 `[[xxxyyy]]`   | 看目标文件名实际字符         |
| `[[xxx、]]`（尾随中文标点）  | `[[xxx]]`                         | 删除多余标点                 |
| `[[xxx,]]`（尾随英文标点）   | `[[xxx]]`                         | 删除多余标点                 |
| `【xxx】`（用了全角方括号）  | `[[xxx]]`                         | 替换为 `[[]]`              |
| `[[xxx] ]`（半个括号）       | `[[xxx]]`                         | 补全括号                     |
| `[[xxx, yyy]]`（含英文逗号） | `[[xxx、yyy]]` 或 `[[xxx yyy]]` | 见上"标题 sanitization 规则" |

**修正完后**，xxx 作为合法双链，**进入标准创建笔记流程**（步骤 4–9）。

### 判定流程图（覆盖主流程与特殊场景）

```
[[xxx]] 未解析（步骤 1-3 定位）
    │
    ├── 检查 [[xxx]] 内部格式（步骤 5：含 , . ? 空格/标点/全角括号）
    │       │
    │       ├── 有问题 → 重写格式（sanitization）→ 修改源文件 [[]]  → 进入创建流程
    │       └── 无问题 ──────────────────────────────────────────┐
    │                                                            │
    └── 进入创建笔记流程（步骤 4-9）  <───────────────────────────┘
            │
            ├── xxx 是名词短语 → 模式 A 概念深潜 / 模式 D 概念拓扑
            ├── xxx 是动词/操作 → 模式 B 实践拆解 / 模式 C 还原论拆解
            └── xxx 是问句/批注/反馈 → 整篇写一篇针对性回答（模式 B 实践拆解）
            │
            └── 步骤 7：文件名 sanitization（去 , . ? 等不支持字符）
            │
            └── 步骤 8：check 校验新文件内部双链
```

### 一句话口诀

> **所有 `[[xxx]]` 未解析 = 创建笔记。** 问句创建回答笔记，批注创建反馈笔记，吐槽创建解释笔记。**绝对不能删、不能改成引用块、不能跳过。** 唯一允许的"重写"是修 `[[]]` 内部格式问题（含 `, . ?` 等 Obsidian 不支持的字符），重写后照样创建。

## 标题 sanitization 规则（创建文件名前必过）

**Obsidian wiki-link 不支持**作为 link 一部分的字符：（半角空格）/ `　`（全角空格）/ `,` / `.` / `?` / `:` / `;` / `*` / `"` / `\` / `<` / `>` / `|` 等。

**新建文件名时：**

1. 如果 link `xxx` 含上述字符，**必须先重写**为合法形式（重命名标题），然后才能作为文件名
2. 重命名原则：
   - `,` → `，`（改用中文标点，保留语义）或直接删除
   - `.` → `。` 或删除
   - `?` → `？`（中文问号）或删除（保留主语）
   - 连续空格 → 单空格
3. **重写后的标题在 vault 里应该能找到对应文件**——别改名后 vault 里没有这个文件
4. **frontmatter `bklink` 和正文里的 `[[xxx]]` 都要同步改**——保持链路一致

**示例**：

| 原 link（不支持）            | 重写后 link + 文件名                                                          |
| ---------------------------- | ----------------------------------------------------------------------------- |
| `[[foo, bar]]`             | `[[foo、bar]]`（文件名 `foo、bar.md`）                                    |
| `[[what is X?]]`           | `[[what is X]]` 或 `[[what is X？]]`                                      |
| `[[1.2.3 协议]]`           | `[[协议 1.2.3]]` 或 `[[协议 1-2-3]]`（避免 Obsidian 把 `1.2.3` 当数字） |
| `[[foo　bar]]`（全角空格） | `[[foo bar]]` 或 `[[foobar]]`（看哪个文件实际存在）                       |

> 命令的 `filename` 字段已自动清掉 `* " \ / < > : | ?`；` , . ?` 这几个**它故意不清**——
> 它们在标题里可能是合法的（见 frontmatter 规范），要你按 vault 现状判断。

## 命令速查（本 skill 用到的 nx-kn 命令）

| 命令                                                                      | 用途                                                 |
| ------------------------------------------------------------------------- | ---------------------------------------------------- |
| `nx-kn obsidian spec`                                                   | **列出登记的规范**（key + 路径 + 是否存在）    |
| `nx-kn obsidian spec --doc <key>`                                       | **取该规范全文**（步骤 0.2 / 步骤 6 / 步骤 8） |
| `nx-kn obsidian get --json`                                             | 取 vault 根 + 规范登记项                             |
| `nx-kn obsidian scan --json`                                            | 扫全库未解析双链（步骤 1 / 9）                       |
| `nx-kn obsidian frontmatter --source <文件> --link "<文本>" [--locate] [--project <项目根>]` | 生成 frontmatter YAML 段（步骤 4；`--project` 用于项目解读模式） |
| `nx-kn obsidian ask --question "<原始提问>" [--project <项目根>]`              | **项目域提问唯一入口**：定位 / 初始化 Base、把提问清洗后以 `[[…]]` 追加到根文档末尾（幂等）、返回答案笔记位置与追加行号；不带 `--question` = 仅初始化根文档 |
| `nx-kn obsidian check --snapshot <文件>`                                | 存未解析链接快照（步骤 8 前）                        |
| `nx-kn obsidian check --snapshot-before <文件> --new-file <相对路径>`   | 差分校验新文件有没有引入新红链（步骤 8）             |

加 `--json` 得机器可读输出；`--vault <绝对路径>` 可临时覆盖配置的 vault。
