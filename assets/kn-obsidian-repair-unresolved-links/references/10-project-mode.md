# 项目解读模式详解（读大项目 → 生成文档 → 双链拷问）

> 主文档：[SKILL.md](../SKILL.md) §「项目解读场景」
>
> 这份 ref 只讲**项目解读这一个场景**的完整打法：初始化（建项目根文档 + 文档树）
> 与提问（用户在 Obsidian 里写 `[[问题]]`，agent 带着源码作答）。
> 主 skill 讲的是通用 9 步流程；这里讲的是「多了个代码库」之后该怎么变。

---

## 什么时候进入这个模式

- 在某个**代码项目**里被要求「读这个项目 / 给这个项目写文档 / 解读一下这个项目」；
- 或者用户在 vault 的**项目文档**里写了 `[[问题]]`（如 `[[为什么爬虫不走代理]]`），
  让你去回答。

两种情况走的是**同一套流程**，只是入口不同：前者先建树再答，后者直接答。

---

## 先定两个根（项目根 ≠ vault 根，绝不能混）

会话通常是在**项目根**启动的——最容易出的错就是把项目根当成 vault 根。

| 根                 | 是什么                 | 怎么确定                                                                       |
| ------------------ | ---------------------- | ------------------------------------------------------------------------------ |
| **项目根**   | 被解读的代码库         | 用户明确指定就用指定路径；否则在项目目录运行 `git rev-parse --show-toplevel` |
| **vault 根** | 文档与双链所在的知识库 | `nx-kn obsidian get --json` 的 `vault` 字段（面板设一次即可）              |

**vault 只认 `nx-kn obsidian get --json` 的答案**——它来自用户的配置（面板「Obsidian」页
或 `nx-kn obsidian set vault=…`），**skill 不自己选库**。

判定 `source` 字段：

- `store` / `env` / `kb` = 用户明确配置过，直接用；
- `cwd` = 从当前目录沿父目录**猜**出来的——在项目根场景下大概率不是你要的库，**停下来向用户确认**；
- 未设置（`configured:false`）→ 问用户要 vault 路径，设置一次（面板或 `nx-kn obsidian set vault=…`）。

**两个根的分工**：文档路径相对 **vault 根**；代码路径相对 **项目根**。答案引用代码时用项目根拼绝对路径。

## 场景一：初始化项目知识树

**调用本 skill 并要求解读项目时，就执行这一段**——不用先问「要不要建根文档」。

### 1. 项目名、目录与根文档

项目名按**三级**确定，顺序不可换：

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1 | `--project-name <名字>` | **推荐**。目录名是给人看的阅读目录名，不该被 npm 包名绑架（包名可能带 scope、可能留着产品线早期的版本号） |
| 2 | 已有根文档的绑定 | `projects/<名>/Base-<名>.md` 的 `project:` 等于本项目绝对路径时沿用该名字 |
| 3 | 自动推导 | package.json 的 `name` → Cargo.toml / pyproject.toml 的项目名 → 仓库目录名（去非法字符与 scope 前缀） |

**名字一旦定下就不要改**：它同时决定目录、根文档文件名、以及每篇笔记 `bklink` 里的
`[[Base-<名>]]`。改名一次，该项目的全部笔记会在一瞬间集体变红链。

显式名字必须**原样可用**：含路径分隔符、或会被清洗（如 `*`）时直接报错，脚本不替人改写；
名字已被另一个项目绑定也直接报错，不覆盖别人的树。目录存在但没有根文档（早期手写笔记）
则允许接管——那是给无主笔记补项目身份的唯一路径。

项目知识树固定初始化到：

```text
<vault>/projects/<项目名>/Base-<项目名>.md
```

`Base-<项目名>.md` 是这棵知识树的**根节点**。它的**定位与创建只走脚本**：

```bash
nx-kn obsidian ask --project <项目根> --project-name <目录名>   # 不带 --question：仅定位 / 初始化根文档
```

- **不存在** → 脚本创建目录与根文档，frontmatter（含 `project: "<项目根>"` 绑定）由脚本生成，
  正文只有 `# <项目名>` 一行标题。**不要自己手写、也不要用 frontmatter 命令另建**——
  位置的唯一事实源是 `ask`，agent 自建位置是明令禁止的（见场景二末尾）。
- **已存在** → 脚本原样返回它，什么都不改。

`--project <项目根>` 把 `project: "<项目根>"` 写进 frontmatter——**这是文档与代码库的绑定**，
场景二全靠它找到源码。根文档与每篇项目文档都必须带**同一个** `project` 绝对路径。

### 2. 探索项目

入口文件、目录结构、模块划分、构建与运行方式——用 Grep / Read 实际读代码，**不猜**。

### 3. 生成文档：每篇只讲一个单项

1. **一篇 = 一个单项**：一个模块、一条关键流程、一个关键机制、一处设计取舍。
   不写「本项目架构全景」「读前必看 / 三句话总结 / 常用核对命令 / 维护建议」这种
   什么都要说一点的元文档——它既讲不清任何一件事，又很快过期。
2. 落盘位置：`<vault>/projects/<项目名>/` 下，frontmatter 运行：

   ```bash
   nx-kn obsidian frontmatter --source <项目里最相关的源文件> --link "<单项标题>" --project <项目根绝对路径>
   ```
3. **关系靠双链建立，不靠手工维护清单**：

   - 子文档的 frontmatter `bklink` 指向**父节点**（模块文档 → 根文档；子项文档 → 模块文档）；
   - 父文档正文里放一条指向子文档的双链；
   - 于是 Obsidian 的链接关系图自然长成一棵树——**不需要在根文档里维护「文档树」区块**。
4. **根文档只做树根**：放一级模块的双链即可，不写摘要、不写导航、不写维护建议。
   它的价值是「一个稳定的入口」——用户从它进入，顺着双链往下走。
5. 创建 / 修改后跑 `nx-kn obsidian check`，确保树里的双链都能解析。

## 场景二：项目域提问（`[[问题]]` → 脚本建两条关系 → 标准 9 步）

用户（你）在 OB 里打开项目根文档或任一子文档，直接写 `[[问题]]`；或者在对话里直接问项目相关问题。
**第一步永远是同一条脚本**，位置与 frontmatter 只由它决定：

```bash
nx-kn obsidian ask --question "<原始提问>" --project <项目根绝对路径> [--project-name <目录名>] [--source <出处文档的 vault 内相对路径>]
```

脚本做且只做四件事：

1. 定位（首次则初始化）`<vault>/projects/<项目名>/Base-<项目名>.md`（frontmatter 带 `project` 绑定）；
2. 把提问**清洗成合法文件名**（`? : \` 等非法字符去掉），以 `[[清洗后]]` **追加到根文档末尾**——
   同一提问重复提交不重复追加（幂等）；原文与清洗后的差异在输出的 `question.rewritten` 里；
3. **建立两条关系**（同一个 `[[问题]]` 链接，两个落点，指向同一篇答案笔记）：

   | 关系                   | 链接在哪               | 谁写的                     |
   | ---------------------- | ---------------------- | -------------------------- |
   | **Base ↔ 目标** | 根文档末尾那一行       | 脚本追加                   |
   | **出处 ↔ 目标** | 出处文档里用户写的那行 | 用户（脚本只核对，不改它） |

   两处都在是**正常且预期**的——不是重复，是两个入口指向同一篇答案笔记。
   `--source` 只是让脚本核对「出处那篇里确实有这个双链」，对不上会如实报「请核对出处」。
4. 返回本次要用的全部定位信息：`base.rel`（根文档相对路径）、`line`（提问所在行）、
   `note.path`（答案笔记该写到的位置）、**`note.frontmatter`（目标笔记的 frontmatter，照抄）**、
   `project`（项目根）。

目标笔记的 frontmatter 长这样（由脚本生成，不要自己编）：

```yaml
---
creatime: 2026-10-23 18:19:14
tags: []
bklink:
  - "[[Base-dataweb]]"
  - "[[是不是就是物理机层面的 Node是不是就是物理机相关层面的绑定概念 一个Node就是一个物理机 或者说对应一个物理IP]]"
project: "D:\\code\\a_sh_cmd_utils\\proj\\dataWeb"
---
```

`bklink` 两项：**根文档（父）+ 问题链接（这次回答的是哪一问）**；`project` 把这篇笔记绑到代码库。

然后照**主 skill 的标准 9 步**走，占位全部从脚本输出取，**不再自行定位**：

- 步骤 3 的出处 = `base.rel` + `line`（脚本已给，不用再 Grep）；
- 步骤 4 = **直接用 `note.frontmatter`**（不要再单独跑 frontmatter 命令，避免两处形状不一致）；
- 步骤 6 **必须读项目源码**——读 source 的 `project` 字段定位代码库，从问题出发读代码到能回答为止，
  答案引用 `文件:行号`、实际行为、设计取舍；发现文档写得不对也要当场指出；
  **产出必须是「回答这个问句」的正文**，不是「这条问句是什么」的说明：
  - ❌ `本条为模板自动插入的 stray link，非读者提问。对应内容见 XXX.md` —— 这是**没回答**；
    红链还在，答案没长出来；
  - ✅ 读源码 / 读相关笔记，把这个问句**当成真的问题**答出来（具体做法、命令、代码位置）；
  - 问句看起来不像提问（模板插入、占位文本、像笔误）**不构成跳过的理由**——
    要么写出实质回答，要么**先问用户**「这条要答吗」。
- 步骤 7 写到 `note.path`（`projects/<项目名>/<link>.md`）——**这就是答案笔记的唯一位置**；
- 步骤 8 / 9 照旧（snapshot diff + `head -3` 复查）。

> ⚠️ `Base-<项目名>.md` 是树的稳定入口：用户之后在根文档或任一子文档提问，
> 都沿 `project` 字段回到同一个源码仓库——不靠 cwd 猜。

### 明令禁止（历史教训：agent 反复冗余地建树建索引）

- ❌ **自行决定答案笔记的位置**（vault 根 / 项目根 / 新建目录）——位置只有 `note.path` 一个答案；
- ❌ **自己拼 frontmatter / 自己写 bklink**——照抄 `note.frontmatter`（bklink 两项：根文档 + 问题链接）；
- ❌ **每次提问新建「文档树」「索引」「MOC」「清单」文件**——树只靠 bklink 长出来，这类文件一个都不建；
- ❌ 在根文档里维护提问列表 / 目录——脚本追加的 `[[提问]]` 就是全部记录，不整理、不去重、不重排；
- ❌ 手写 frontmatter（步骤 4 的命令生成）；
- ❌ **用一段元说明代替回答**（「本条非读者提问 / 对应内容见 XXX.md」）——红链留着、答案丢掉，
  等于没做；真答不了就问用户；
- ❌ Base 已存在时重写 /「整理」它——脚本对已存在的根文档只追加、不改写；
- ❌ 改出处文档——脚本只核对，那篇文档里的 `[[问题]]` 是用户的，不是脚本的。

## 场景三：多项目并发时的范围隔离

一个 vault 里可以并存多个项目的笔记树（`vault/projects/<项目名>/`）。**每个项目只该动自己那份**——
否则两个项目同时跑，各自会去修对方项目里的红链，笔记越改越乱。

先看有哪些项目（只读枚举，不建任何文件）：

```bash
nx-kn obsidian projects          # 每个项目：篇数 / 根文档是否就位 / 代码库绑定(project:) / 未解析链接数 / 文档清单
nx-kn obsidian projects --json   # 机读
```

`Base-<项目名>.md` 显示「缺」时**不要自己补**——建根文档的唯一入口是下面的
`ask --project`，这样 frontmatter 的 `project` 绑定不会两处写歪。

项目域的**扫描与校验都要带 `--project <项目根>`**；建议同时带 `--project-name <目录名>`，
三条命令用**同一个**名字——各自推导一次就可能算出三个不同目录：

```bash
nx-kn obsidian scan --json --project <项目根> --project-name <目录名>                 # 只扫本项目的红链
nx-kn obsidian check --snapshot snap.json --project <项目根> --project-name <目录名>   # 快照
nx-kn obsidian check --snapshot-before snap.json \
    --new-file "projects/<项目名>/<笔记>.md" --project <项目根> --project-name <目录名>  # 差分
```

- **哪些文件里的链接会被收集**：只看 `vault/projects/<项目名>/`。
- **链接能否解析**：仍对照**全库**——链到共享笔记 / 别的项目的笔记不算红链，
  否则 agent 会跑去重复建一份（那才是真正破坏隔离的地方）。
- 快照与差分**两次要带同一个 `--project` 与 `--project-name`**，否则范围不一致，差分没有意义。
- 项目目录还没初始化时，命令会如实提示「先跑 `nx-kn obsidian ask --project … --project-name …` 建根文档」——
  提示里的名字就是它当时算出来的那个，直接复制即可，不报错、也不静默扫全库。

不带 `--project` 就是全库扫（修整个 vault 的红链时用）。

## 迁移：导出 / 导入 zip

项目树可以整包搬走（换机器、备份、给同事）。包是普通 zip，里面只有
`manifest.json` 和 `projects/<名>/…`——**没有索引、没有配置、没有本机路径**（路径只作为信息记在 manifest 里）：

```bash
# 源机器：导出一个或多个项目
nx-kn obsidian export --name sedoc-fe-8.60 --out D:\backup\sedoc.zip
nx-kn obsidian export --name a,b --out D:\backup\two.zip
nx-kn obsidian export --all --out D:\backup\all.zip

# 不写 --out 也行：包落在**当前目录**，名字是 kn-<项目|all>-<时间戳>.zip，命令会打出完整路径
nx-kn obsidian export --name sedoc-fe-8.60

# 目标机器：先预演，再导入
nx-kn obsidian import --file D:\backup\sedoc.zip --dry-run
nx-kn obsidian import --file D:\backup\sedoc.zip
```

面板里这两步不用敲命令：**「导出到」留空 = 包直接回给浏览器下载**
（下载名服务端定：`kn-<项目>-<时间戳>.zip`）；导入直接**把 zip 拖进投放区**——
浏览器只交得出字节拿不到本地路径，路由层把它落成临时文件后走同一条导入逻辑
（请求结束即删，回显的是原始文件名）。

要点：

- **manifest 是唯一权威**：导入以它列出的文件为准，逐条校验 sha256；包里多出来的条目
  忽略并列进 `ignored`——不认识的字节绝不落盘。
- **同名项目默认拒绝**（不合并、不自动改名）。确认覆盖加 `--force`，覆盖前把旧目录
  **整份备份**到数据目录的 `backup/import-<时间戳>/`；覆盖 = 替换，包里没有的旧文件不会残留
  （否则会留下「看起来能解析」的陈旧笔记）。
- **`project:` 绑定默认原样保留**。换机器后原路径通常不存在，导入会在 `projectPathExists`
  里如实标出来；要改就显式给 `--project-path <新的代码库绝对路径>`（该目录必须存在），
  只改 `Base-<名>.md` 的那一行，其他笔记一个字节不动。
- **索引不在包里**，也不该在：`.zvec-grep` 绑死绝对路径与 embedding 模型维度。导入后跑
  `nx-kn kb index`（换过模型用 `--rebuild`）。
- 校验是**先全部跑完再动盘**的：缺文件 / 哈希不符 / 路径非法，任何一项不合格就一个文件都不写。
- 迁移后先跑 `nx-kn obsidian projects` 确认篇数与根文档就位，再跑
  `nx-kn obsidian scan --project <项目根> --project-name <名>` 确认红链为 0。

## 常见坑

| 坑                                                  | 后果                                                 | 正确做法                                                                 |
| --------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------ |
| 把项目根当 vault 根                                 | 文档写进代码仓库里，或扫错库                         | vault 只认 `nx-kn obsidian get --json` 的答案                          |
| **项目名直接吃 package.json 的 name**             | 目录名与人的认知错位（`sedoc-fe-1.0` vs `sedoc-fe-8.60`），根文档一建就与已有笔记的 bklink 全错开 | 用 `--project-name` 显式给「给人看的目录名」；名字定下后不要改         |
| 每篇文档的 `project` 写成不同路径                 | 提问时找不到对应源码                                 | 全树用**同一个**项目根绝对路径                                     |
| **agent 自行决定位置、建树 / 索引 / 清单**    | vault 里长出重复的结构文件，位置漂移，用户明确不期望 | 位置只由 `nx-kn obsidian ask` 的返回值决定；除 Base 外不建任何结构文件 |
| **自己拼 frontmatter（bklink 少一项或写错）** | 答案笔记与树失联，回链断裂                           | 照抄 `note.frontmatter`：bklink = 根文档 + 问题链接，project = 项目根  |
| **出处文档里的双链被当成「重复」而删掉**      | 用户的问题被抹掉                                     | Base 与出处各有一条，指向同一篇答案笔记——两处都在是预期，不是重复      |
| 在根文档里手工维护「文档树」清单                    | 清单必然过期，且掩盖了真实关系                       | 关系由双链表达；根文档只放一级模块的链接                                 |
| 写成一篇什么都讲的架构总览                          | 讲不清任何一件事，且很快过期                         | 一篇 = 一个单项                                                          |
| 文档平铺、没有层级                                  | 几十篇文档彼此不链接，关系看不出来                   | bklink 指父节点 + 父文档回链，关系自然成树                               |
| 只凭文档内容回答问题                                | 答案正确但空洞，拷问落空                             | 步骤 6 必须读源码，引用 `文件:行号`                                    |
