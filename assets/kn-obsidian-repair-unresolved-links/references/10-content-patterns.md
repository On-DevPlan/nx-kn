# 内容生成规范（步骤 6）

> 主文档：[SKILL.md](../SKILL.md) §「步骤 6：生成内容」

本规范是源 skill 的 `reffence/content-spec.md` 提炼。四种模式按主题选择：

| xxx 形态 | 推荐模式 |
| -- | -- |
| 名词短语 / 概念 | 模式 A 概念深潜 / 模式 D 概念拓扑 |
| 动词 / 操作 / 系统机制 | 模式 B 实践拆解 / 模式 C 还原论拆解 |
| 问句 / 批注 / 反馈 | 模式 B 实践拆解（针对提问写一篇回答） |

---

## 通用准则

锚点前置、量级感知、trade-off 讨论。这三条是所有模式的共同基底。

### 锚点前置

> 第一段必须先给**具体问题**或**反直觉现象**，不要从"什么是 X"开始。

```markdown
✅ 好的开场：
"我以为 EventLoop 线程数等于连接数，看了源码才发现它固定为 CPU 核数的 2 倍。Channel 一旦绑定，终身不变。"

❌ 坏的开场：
"EventLoop 是 Netty 的核心调度组件，它负责..."
```

### 量级感知

> 用具体数字，不用"快"、"慢"、"大量"。

```markdown
✅ "redisson 看门狗续期间隔 30s，锁默认过期时间 30s"
❌ "redisson 看门狗续期很频繁，锁很快过期"
```

### trade-off 讨论

> 展示工程妥协而非列出"优点"。

```markdown
✅ "PoolChunk 用二叉树管理内存——代价是分配路径上多 2 次寻址，但换来碎片率从 12% 降到 0.8%，对长期运行的服务值得。"
❌ "PoolChunk 用二叉树有很多优点。"
```

## 模式 A：概念深潜

**适用**：名词短语、单一概念。

**骨架**：

```
1. 锚点（一个反直觉的事实 / 一个具体问题）
2. 是什么（精确定义，给标准 / 给边界）
3. 为什么（从原理 / 历史 / 约束推导出当前形态）
4. 边界（什么场景失效、什么时候不该用）
5. 反例（常见误解）
```

**好坏对照（来源：源 skill 的 content-spec.md）**：

| 维度 | 好 | 坏 |
| -- | -- | -- |
| 结构清晰 | 是 → 怎么做 → 为什么（用层级标题 + 表格） | 知识堆砌、读者多次跳读才能拼图 |
| 高信噪比 | 加粗标记关键参数、用表格对比 | 背景铺垫、口语化填充词（"简单来说"、"我们要注意"） |
| 工程视角 | 给出标准（CRC-32 IEEE 802.3）、类名/函数名 | 用"随意取值"、"仅为演示" |
| 视觉辅助 | 抽象概念 / 复杂计算路径配图（CRC 计算） | 用图做装饰而非解释 |
| 严谨性 | 明确指出"规则边界"（如 `N = L - 1`） | 把"练习用简化"与"工业标准"混为一谈 |

**风格：肯定句优先**

引入概念时直接用肯定句定义，避免"不是 X 而是 Y"的对比式句法：

```
✅ "PooledByteBufAllocator 是 Netty 的内存池分配器..."
❌ "它不是 JDK 默认的 ByteBufAllocator，而是 Netty 自己的 PooledByteBufAllocator。"

✅ "EventLoop 线程数固定为 CPU 核数的 2 倍。Channel 一旦绑定 EventLoop 就终身不变。"
❌ "EventLoop 线程数不是连接数，Channel 也不是随便绑定的，而是终身绑定一个 EventLoop。"

✅ "PoolChunk 的二叉树节点大小按 16B 对齐分配。"
❌ "PoolChunk 内部的二叉树不是任意切分的，而是按 16B 对齐的。"
```

> "不是 X 而是 Y" 反转式句法把否定当作铺垫，强迫读者先在脑中"取消"前一个概念，再建立新概念——多一层认知负担。

## 模式 B：实践拆解

**适用**：动词、操作、问句回答。

**骨架**：

```
1. 锚点（一个翻车案例 / 一个具体场景）
2. 时序 / 步骤列表（每步对系统产生的具体影响）
3. 表格对比边界（不同实现 / 不同配置的差异）
4. 暴露源码级细节（类名 / 函数名 / 数据结构）
5. 何时失效 / 不要照搬
```

**示例骨架（Netty 内存）**：

```markdown
# Netty PoolChunk 内存池

## 一句话结论
PoolChunk 通过 PooledByteBufAllocator 实现零拷贝——但路径上要过 PoolArena、PoolChunkList、PoolSubpage 三层管理。

## 分配时序

| 步骤 | 操作 | 影响 |
|------|------|------|
| 1 | PoolArena 接管分配请求 | 减少锁竞争；多 Arena 分摊 |
| 2 | PoolChunkList 按使用率分层 | 回收优先用满 chunk，避免碎片 |
| 3 | PoolSubpage 按 16B 对齐切分 | 小对象也能用池化 |
| 4 | 二叉树节点标记 | O(log n) 分配 |
```

## 模式 C：还原论拆解

**适用**：系统机制（要解释"为什么这样设计"）。

**骨架**：

```
1. 整体行为 / 用户视角的表象
2. 自顶向下分解：L1 / L2 / L3 / L4（每一层一段）
3. 每层回答「这一层做什么、依赖下层什么」
4. 跨层耦合点（哪里某层的约定需要上层遵守）
```

**示例（keyset 跨页）**：

```
L1 API 层：cursor 参数是上一次响应的 nextCursor
L2 查询层：WHERE id > ? ORDER BY id LIMIT N
L3 索引层：依赖 B-tree 的有序扫描
L4 存储层：MVCC 下新写入的 id 在扫描范围外（keyset 不感知）
→ 推导：并发写入场景下，新数据不会出现在 keyset 翻页结果里
```

## 模式 D：概念拓扑

**适用**：一组相互关联的概念（讲一个生态、一种关系网）。

**骨架**：

```
1. 锚点（一个具体的「为什么这些概念放在一起」的问题）
2. 概念清单 + 它们之间的边
3. 关键转折点（哪个概念打破了线性叙事）
4. 在 vault 内的位置（这条笔记解决了什么更大的疑问）
```

## 通用反例

**避免过度拟人化**：

```
❌ "小孙子，听爷爷说，redisson 这个锁啊..."  ← 信息密度低
```

**避免模糊与回避**：

```
❌ "至于补零的个数嘛，大概是 L-1 左右..."  ← "左右"掩盖规则
```

**避免结构混乱**：知识点堆砌没有先后逻辑。

**避免缺乏严谨性**：把"练习用简化模型"与"工业标准"混为一谈。
